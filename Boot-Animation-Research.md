# Исследование настоящей boot-анимации — 12.11.2026

## Проверенная машина и границы

ASUS TUF Gaming A15 FA507XI_FA507XI, BIOS FA507XI.314 (CIM). Пользователь хочет движение во время загрузки Windows, не ролик после входа. На этом этапе только поиск и чтение: EFI/BCD/BIOS/системные шрифты не менялись, новых загрузчиков не установлено.

## Найденные реализации

- [AnimeBoot](https://github.com/helloyork/AnimeBoot), ревизия f1af51ce615a1c16d1cbd4f4ad2f9af73defd2c9. Исходник изучен в отдельной папке work/animeboot-review. AnimeBoot.c:454 вызывает AbPlayFromPackage, :491 восстанавливает GOP, :506 вызывает AbLaunchNextStage, :1827/:1835 LoadImage/StartImage. Следовательно, это последовательное воспроизведение ДО Windows, не параллельная анимация при загрузке ядра. docs/firmware-notes.md содержит пример лабораторного запуска и указывает, что Secure Boot в лабораторной VM выключен. Подпись описана в документации, но совместимость на данном ASUS и с FACEIT не проверена. LoopCount=0 без лимита времени не заканчивается — при будущем прототипировании обязателен конечный лимит.
- [Lenovo UEFI Logo Changer](https://github.com/chnzzh/lenovo-logo-changer): GIF и сообщения об анимации на некоторых Lenovo. Это зависимость от модели/прошивки, не готовый способ для данного ASUS. Поддержка анимации FA507XI не найдена; это результат поиска, не доказательство абсолютной невозможности.
- [Windows 7 Boot Updater](https://github.com/coderforlife/windows-7-boot-updater): настоящая замена кадров, но программа предназначена для Windows 7. Не устанавливать её в Windows 11.
- [Microsoft BGRT](https://learn.microsoft.com/en-us/windows-hardware/drivers/bringup/boot-screen-components): передаёт bitmap, не произвольный анимационный поток.
- [UEFI Boot Services](https://uefi.org/specs/UEFI/2.10/07_Services_Boot_Services.html): ExitBootServices прекращает timer services. Инженерный вывод: обычный EFI-проигрыватель нельзя просто оставить на UEFI-таймере работать до рабочего стола; нужен другой механизм отрисовки после передачи управления ОС.

## Более близкое направление: кадры штатного индикатора

Чтение C:\Windows\Boot\Fonts\segoe_slboot.ttf и segoen_slboot.ttf через fontTools подтвердило наличие private-use глифов и таблицы DSIG. Для segoe_slboot.ttf: 241 private-use glyph; просмотр первых 128 (начиная с U+E052) показал кадры вращающихся точек. Контактный лист сохранён только в work/animeboot-review/font-glyph-review.png. Файлы шрифта не копируются в репозиторий и не изменяются.

Это прямое подтверждение наличия кадров, но НЕ доказательство, что текущая сборка Windows выбирает именно эти файлы/глифы для используемого индикатора. Наличие DSIG не является проверкой действительности подписи. Замена глифов потенциально позволит изменить форму монохромного индикатора; цвет задаётся отрисовщиком и этим не решён. Рабочего проверенного метода установки на текущую Windows с Secure Boot не получено.

Следующее полезное исследование: определить реально читаемые boot-ресурсы и путь отрисовки на этой сборке, проверить требования проверки целостности, затем разработать ограниченный прототип и отдельный способ восстановления. Не обещать, что простая подмена TTF даст анимацию Arasaka. Прошивка BIOS пока не имеет обоснованного преимущества для этого требования.

## FACEIT и восстановление

[FACEIT: TPM attestation failed](https://support.faceit.com/hc/en-us/articles/20669555338268-TPM-attestation-failed) прямо запрещает самоподписанные загрузчики в проверяемой цепочке и предлагает запуск напрямую через Windows Boot Manager. Подпись для Secure Boot сама по себе не даёт совместимость с античитом. Существующий переключатель режима может исключить отдельный EFI-проигрыватель, но не откатит общие изменённые файлы Windows.

Батник в безопасном режиме достаточен только если Windows способна загрузиться в этот режим. Для сбоя до запуска ОС нужен внешний путь восстановления; существующие CMD не объявлять защитой от неудачной прошивки BIOS или любого патча winload.

Решение этапа: AnimeBoot оставить кандидатом только для отдельной предзагрузочной заставки; настоящую замену индикатора рассматривать как исследование ресурсов Windows, а не готовую установку. Систему по результатам поиска не менять.
## Проверка кода и прототип — продолжение 12.11.2026

### Что подтверждено непосредственно

Collect-Boot-Indicator-Audit.ps1 выполнен exit=0: временно смонтировал ESP на свободную S:, скопировал Boot Manager, два EFI-шрифта, winload, bootvid и два Windows-шрифта; сравнил SHA256 копий и оригиналов; сохранил экспорт BCD и перечисление настроек. ESP отмонтирован (S: отсутствует). SecureBoot=True. Актуальная папка указана в CyberDeck/backup/boot-indicator-latest.txt. Это снимок для восстановления, не установленная модификация и не проверенный аварийный загрузочный носитель.

Исполняемый Boot Manager на ESP отличается от копии в C:/Windows/Boot/EFI несмотря на одинаковую версию 10.0.28000.342. Поэтому выводы первоначального анализа были перепроверены на настоящем EFI-файле. SHA256 EFI bootmgfw.efi: D8D85F707B4C1DA37642A91BC3860C405E8022A066DAFD36348D515AD915CE43. Его подпись Valid; PDB RSDS key: 5940A1C852070969F04939CC2F6A9F0E2. Символы получены с https://msdl.microsoft.com/download/symbols/bootmgfw.pdb/5940A1C852070969F04939CC2F6A9F0E2/bootmgfw.pdb .

Статический разбор с pefile, парсером публичных MSF/PDB-записей и Capstone:

- AnFwConfigureProgressResources начинает с U+E052; AnFwpProgressAnimation (RVA 0x27F124) доходит до U+E0CB и вызывает BgpTxtDisplayCharacter. Видимый диапазон составляет 122 символа; код также имеет промежуток без отрисовки. Это подтверждённый путь внутри Boot Manager, а не трасса исполнения всех стадий реальной загрузки Windows.
- BfiLoadFontFile (RVA 0xBE7D4) после открытия файла вызывает BlImgVerifyFontIntegrity (вызов RVA 0xBE84C), проверяет результат и при ошибке возвращается. Внутри проверки есть ImgpValidateImageHash. Следовательно, простую замену TTF нельзя объявлять рабочей.
- Get-AuthenticodeSignature для двух оригинальных шрифтов C:/Windows/Boot/Fonts вернул Valid. Для EFI-копий — UnknownError: выбранный поставщик доверия не поддерживает форму субъекта. Это НЕ доказательство повреждения/отсутствия подписи EFI-шрифтов.
- Для текущих winload 10.0.26100.9949 и ntoskrnl 10.0.26100.9974 точные PDB URL вернули HTTP 404. Их путь анимации не подтверждён; нельзя переносить анализ Boot Manager на весь интервал до экрана входа. Символы bootvid получены, подходящих имён анимации в выбранном поиске не найдено.

### Откат и FACEIT

Switch-Boot-Mode.ps1 -Mode FACEIT -CheckOnly выполнен exit=0, целевая запись {bootmgr}; порядок загрузки в этом этапе не менялся. Существующий Boot-FACEIT.cmd остаётся переключателем на обычный Windows Boot Manager. Сам запуск FACEIT по-прежнему не проверен.

Снимок содержит исходные файлы и BCD, но автоматически восстанавливать ВСЕ эти файлы после будущих обновлений Windows нельзя. Для будущего установщика обязательны журнал конкретно изменённых путей с исходными/установленными хешами, восстановление только этих путей, проверка оригинальной цепочки перед FACEIT и независимый путь восстановления до старта Windows. Безопасный режим не спасает сбой, который происходит раньше него. Проверка/откат должны быть привязаны к фактически установленному варианту; сейчас откатывать нечего, прототип не установлен. Старые батники оформления и переключения сохранены.

Результат: механизм кадров установлен для реального EFI Boot Manager, подготовлен проверенный графический прототип и снимок оригиналов. Подтверждённого способа установки с сохранением текущих требований Secure Boot/FACEIT нет. Не отключать проверку подписей и не патчить winload по неподтверждённой инструкции ради первого теста. Следующее исследование — подтвердить путь анимации winload/kernel данной сборки и способ изолировать ресурсы от чистого режима; до этого не создавать пункт загрузки, обещающий рабочую Arasaka-анимацию.

## Реальная анимация, Secure Boot и установка — 13.11.2026

**Текущее состояние:** отдельный экспериментальный пакет установлен на ASUS FA507XI, но физический запуск ещё не выполнялся. Первый тест запускается вручную по [Boot-Animation-Test.md](Boot-Animation-Test.md). Постоянный UEFI-порядок сохранён, ожидающего BootNext нет, `bootuxdisabled` вернулся к прежнему `Yes`. Не путать успешную загрузку стенда с проверенной загрузкой установленной Windows.

### Подтверждённый механизм

- В шрифте есть два диапазона: 122 кадра U+E052–U+E0CB для старых точек и **119 кадров U+E100–U+E176 для современного кольца**. Замена только первого диапазона реально запускалась, но не меняла кольцо. `experimental/make-lab-font.py` заменяет оба диапазона и сохраняет остальные символы.
- Собственный EFI-модуль меняет в памяти только font verifier, путь boot-шрифта и однократный переход bootmgr → winload. Проверяются exact-build timestamp/checksum/SizeOfImage, прологи и уникальная строка пути. Дисковые Windows PE-файлы не патчатся; ядро/DSE/PatchGuard/runtime services не изменяются. Проверка только шрифта возвращает успех для текущего загрузочного компонента, то есть экспериментальная цепочка осознанно отличается от штатной цепочки доверия.
- `\boot\fonts\segoe_slboot.ttf` заменяется на равнодлинный `\aras\fonts\segoe_slboot.ttf`. Оригинальные `Boot\Fonts` остаются неизменны. Новые ресурсы: `EFI\Microsoft\aras\fonts` и `Windows\aras\fonts`.
- Цепочка: подписанный shim → новый модуль `grubx64.efi` с доверенным MOK-хешем → оригинальный HackBGRT → оригинальный bootmgfw → winload. Одноразовый LoadImage hook восстанавливает исходный API и CRC таблицы **до** вызова загрузки Windows; оригинальный API по-прежнему проверяет загружаемый файл. Не используется готовый EfiGuard или его общий обход проверок образов, PatchGuard/DSE.
- Новый модуль имеет собственный SBAT-раздел. Без него shim отвергал файл даже при добавленном MOK-хеше. Без MOK-хеша окончательный файл также был отвергнут: отрицательный контроль прошёл.

### Проверки настоящей загрузки

Использован маленький автономный стенд: встроенный WinRE WIM, отдельный BCD и MBR/FAT32 image, QEMU TCG (2 CPU, 2560 MB), без сети/физических дисков/общих папок. QEMU не установлен сервисом. Скрипт завершает гостя; временные записи гостя идут в overlay. Полная Windows/VM-диск не устанавливались.

В первых Secure Boot опытах штатный и изменённый загрузчики одинаково останавливались с 0xc000000f. ### Установка и откат на ноутбуке

- `Build-Boot-Animation-Package.ps1` подготовил `%USERPROFILE%\CyberDeck\boot-animation-v1`. `Manage-Boot-Animation.ps1` установил 10 новых файлов и отдельную запись `Arasaka Animation (experimental)`. Оригинальные Microsoft/HackBGRT файлы сверены по 9 хешам и не перезаписаны. Secure Boot=True, BitLocker был Off/FullyDecrypted; его настройки не изменялись.
- Выполнен реальный цикл **Install → TestRoundTrip → Restore → Install → Check**. Откат удалил отдельную запись и собственные файлы, следующий Install подтвердил отсутствие конфликтующих файлов. Проверка BootNext и bootuxdisabled прошла с восстановлением. В первом запуске PowerShell 5.1 не разобрал UTF-8 без BOM; до исправления кодировка не позволила создать даже журнал. Установленный скрипт и исходник теперь UTF-8 BOM.
- `Restart-For-FACEIT.ps1 -Action TestRoundTrip` повторно прошёл. `Switch-Verified-Boot-Mode.ps1 -Mode FACEIT -CheckOnly` прошёл: SecureBoot=True, 7 исходных файлов, включая ядро и подписи. Сам FACEIT не запускался; его допуск не гарантируется одним этим тестом.
- Рабочий стол: Test-Arasaka-Animation.cmd, Cancel-Arasaka-Test.cmd, Restore-Arasaka-Animation.cmd, Arasaka-Animation-README.md. Существующий Restart-For-FACEIT.cmd сохранён. Тестовый CMD после сохранения работы и нажатия клавиши сам выставляет одноразовый запуск и запрашивает перезагрузку без /f; **в работе агента этот CMD не запускался**.
- Первое MOK-подтверждение: `EFI/ArasakaAnim/grubx64.efi`. После перезагрузки MOK одноразовая запись уже израсходована — тестовый CMD нужно запустить повторно. Запись доверия относится только к точному PE/COFF-хешу, отключение Secure Boot не требуется. Откат не очищает общую MOK-базу.
- При сбое до Windows выбрать Windows Boot Manager в UEFI; после входа можно удалить эксперимент CMD-откатом. Один безопасный режим не является средством восстановления до запуска ОС.
